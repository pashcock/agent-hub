# Возможности провайдеров в agent-hub

Сверено с кодом 2026-10-27, после обновления Kimi-профиля. Таблица описывает
адаптеры hub, а не все возможности самостоятельных CLI. Версии провайдеров,
профили и конфигурация MCP могут менять поведение; при изменении адаптера
обновлять соответствующие строки здесь.

## Режимы и ограничения

`ask`, `plan`, `review` — режимы API hub. Их названия не означают автоматическое
включение одноимённого режима провайдера. Для трёх адаптеров ниже они выбирают
одинаковую политику локального read-only; назначение работы задаётся текстом задачи.

| Возможность | Kimi | Grok | Codex |
|---|---|---|---|
| Backend | `kimi acp`, процесс на беседу | Нативный ACP, процесс на беседу | Общий `codex app-server`, thread на беседу |
| `ask / plan / review` | ACP `default`/`manual`; allowlist чтения, поиска, web и MCP; клиент запрещает запись и создание терминала | Нативный `read-only`, Auto выключен; дополнительные permission requests отклоняются | Нативный `read-only`, `approvalPolicy=on-request` |
| `code` | ACP `yolo` — Ask When Needed; встроенный dangerous-command guard включён | Нативный `workspace`, `autoMode=true`, `yoloMode=false` | `workspace-write`, `approvalPolicy=on-request` |
| Обычная работа в `code` | Запись и команды внутри проекта без повторного approval клиента | Нативный Auto решает, когда нужен запрос | Нативная политика/sandbox решает, когда нужен запрос |
| Запросы разрешений | Нативные approvals → hub; клиент дополнительно запрашивает внешние пути записи/терминала, privilege escalation и нестандартное окружение | Нативные approvals → hub в `code` | Нативные command/file/permissions approvals → hub |
| OS sandbox | Адаптер не предоставляет; ограничения инструментов и клиентских ACP-операций | Есть нативный sandbox; `sandboxed_read_only=false` заявлен консервативно | Есть нативный sandbox; `sandboxed_read_only=true` |
| Явный `sandbox` | Не поддерживается | Только `read-only` для режимов чтения или `workspace-write` для `code` | Передаётся провайдеру без собственного allowlist hub; перекрывает значение, полученное из `mode` |
| Сеть | Hub не ограничивает | Зависит от нативной политики/sandbox | Зависит от нативной политики/sandbox |
| MCP | Пользовательские из `source_home/mcp.json` и нативные проектные MCP; доступны и в режимах чтения | Пустой список при создании сессии; импорт MCP других harness выключен; это не общий запрет любого MCP | MCP собственного профиля, кроме отключённого agent-hub |
| Защита от рекурсивного agent-hub | Фильтрация импортируемых имён, запрет стандартных имён инструментов; токен удалён из окружения | Проверка нативного списка MCP перед prompt; токен удалён | Сервер отключён на app-server; токен удалён |
| Проектная конфигурация | `local.toml`, `mcp.json`, `plugins` разрешены; `KIMI_CODE_TRUST_WORKSPACE=true` | Проектная политика применяется; импорт чужих профилей выключен; активные плагины `codex`/`superpowers` отвергаются | Нативное поведение Codex |
| `acceptForSession` | Одно действие | Одно действие | Нативное разрешение на сессию там, где его поддерживает тип запроса |
| Восстановление беседы после рестарта/eviction | Да | Да | Да |
| `peer_steer` во время хода | Нет | Нет | Да |
| Native questions / MCP elicitation | Свободный текст в native forms не реализован; вопросы текстом и `peer_send` | Свободный текст в native forms не реализован | Поддерживаются адаптером |

Playwright не встроен в hub: доступен как MCP, если настроен и подключён.
Allowlist инструментов Kimi разрешает `WebSearch`/`FetchURL`; фактическое наличие
зависит от настроенных нативных сервисов. Глобальные hooks/plugins standalone Kimi
не копируются в приватный профиль, но проектная конфигурация больше не запрещена.

Claude остаётся отдельным адаптером; его сравнение с Codex находится в
[README](../../README.md#providers). Эта таблица покрывает Kimi/Grok/Codex,
обсуждавшиеся при выравнивании разрешений; она не отменяет пользовательскую паузу
на вызовы Claude.

## Почему Kimi Plan не равен read-only

У Kimi есть нативный Plan mode. По документации `Write`/`Edit` в нём ограничены
файлом плана, `TaskStop` запрещён, но остальные инструменты, включая `Bash`,
продолжают подчиняться текущим permission rules. Это режим планирования с
ограничениями инструментов, не эквивалент filesystem sandbox `read-only`.

Сейчас hub **не включает нативный Kimi Plan** для `mode=plan`: все три режима
`ask/plan/review` выбирают ACP `default`, выключают native plan по умолчанию и
не предоставляют `EnterPlanMode`/`ExitPlanMode`. Локальные ограничения обеспечивает
allowlist плюс отказ клиента выполнять ACP writes/terminal creation.

Источники: [Kimi Plan tools](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/tools.html#plan-mode),
[режимы permissions](https://www.kimi.com/code/docs/en/kimi-code-cli/guides/interaction#the-three-permission-modes),
[настройка адаптера](../../internal/kimi/setup.go),
[ACP-клиент](../../internal/kimi/client.go).

## Общие границы approvals

- Главный агент отвечает через `peer_approve`. Категории human gate задаются
  конфигурацией: по умолчанию privilege escalation, запись вне `cwd` и изменение
  постоянной политики. Gate применяется к распознанным полям запроса.
- Таймаут по умолчанию — 600 секунд, затем отказ. Это конфигурация, не неизменная
  гарантия: `on_timeout=accept` меняет поведение, в том числе для human-gated запросов.
- Hub не перехватывает все действия внутри harness: общий классификатор видит
  только поступившие approvals. Shell-команда может обращаться к путям, которых
  нет в её структурированном запросе.
- Read-only локального выполнения не ограничивает побочные действия MCP-сервера.
  Проектные настройки считаются доверенными; таблица не описывает изоляцию от
  враждебного проекта или произвольного кода.
- `peer_capabilities` — не одинаково полный inventory для всех адаптеров.
  Например, Kimi сейчас возвращает модели, но не перечисляет подключённые MCP;
  `mcp_servers=null` не означает, что MCP выключены.

## Что ещё не реализовано

1. Codex `item/permissions/requestApproval`: профиль сохраняется для ответа,
   но пути и права не переносятся полностью в поля классификации hub. Поэтому
   human gate записи вне проекта может не сработать. Одобрение возвращает
   запрошенный профиль; это не автоматическая выдача прав без approval.
2. Общий разбор shell-команд: проверка privilege escalation hub пока смотрит
   на первое слово. У Kimi есть дополнительная клиентская проверка и нативный
   dangerous-command guard, но общего полноценного shell-анализатора hub нет.
3. Выравнивание MCP Grok с Kimi/Codex ещё не выполнено.

- Kimi 2.3.2: `TestRealKimiNativePolicyAndProjectMCP` проверяет через изолированный
  MCP hub обычные запись/Bash, проектный MCP и нативный опасный запрос с отказом
  до исполнения. Unit/race-тесты проверяют клиентские границы и формат approvals.
- Рабочий hub обновлён 2026-10-27: подтверждены SHA запущенного бинарника и
  no-prompt ACP-каталог Kimi. Это отдельно от тестов в изолированном hub;
  все клетки таблицы не перепроверялись реальными модельными ходами.
